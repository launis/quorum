    Problem Statement & Architectural Context

    Following the integration of the initial Tavily search tool (mcp_tavily_search) in backend_v2/services/mcp/, Quorum's Model Context Protocol (MCP) tool execution loop supports live external retrieval. However, the MCP tool registry is currently coupled to a single provider (mcp_tavily_search), and backend_v2/services/mcp/mcp_tool_loop.py contains hardcoded assumptions targeting Tavily specifically.

    To provide specialized encyclopedic research and factual anchoring without commercial API costs or search noise, Quorum requires native Wikipedia MCP Tools: 1. mcp_wikipedia_search: Rapid search querying the Wikipedia Action API returning article titles, snippets, page identifiers, and canonical Wikipedia URLs. 2. mcp_wikipedia_read: Detailed content retrieval querying the Wikimedia REST API page summary endpoint, protected by a strict character truncation shield (mcp_wikipedia_max_chars in backend_v2/settings.py) to prevent context window explosion and preserve prompt caching.

Eager Capability Indexing in ToolDispatcher: O(1) capability lookup and deterministic primary search tool resolution preserving explicit step author priority (Step.allowed_mcp_tools). 4. Zero-Provider Orchestrator Pipeline: mcp_tool_loop.py consumes ToolCapability.SEARCH with zero provider name checks, enabling arbitrary future retrieval tools (PubMed, ArXiv, DuckDuckGo, SEC EDGAR, Vector DB) to plug in cleanly without modifying orchestrator code.

    Cloud-Agnostic Secret & Credential Ingress Topology:

    To guarantee enterprise portability across multi-cloud environments (specifically Google Cloud Platform, Amazon Web Services, Microsoft Azure, and on-premise Kubernetes) without coupling tools to cloud-specific SDKs:

    1. Dual Ingress Separation (Runtime Execution Parameters vs. Infrastructure Secrets):
    2. Runtime Execution Parameters (Dynamic per LLM call / Step configuration): Query strings, reasoning rationale, target language codes, step names, and claim texts vary dynamically on every LLM invocation. These are validated fail-fast through strongly typed, immutable Pydantic V2 DTOs (StandardSearchInputDTO and WikipediaReadInputDTO). Allowed tools are configured dynamically per specialist workflow step in Quorum Studio (Step.allowed_mcp_tools).

    3. Infrastructure Credentials & Secrets (Dynamic per environment / Cloud Secret Provider): API keys (specifically: TAVILY_API_KEY), service URLs, passwords, rate limiters, user-agent identifiers, and timeouts represent infrastructure secrets. These are NEVER passed through LLM prompts, NEVER stored in database seeds, and NEVER hardcoded in Python tool logic.

    4. Settings Model as In-Application Anti-Corruption Layer (ACL):

    5. Settings in @[backend_v2/settings.py] (inheriting from Pydantic V2 BaseSettings) acts as the sovereign abstraction wrapper.
    6. MCP tools never directly read .env files, never call os.environ.get(), and never execute cloud vendor SDK calls.

    7. Tools consume settings strictly via typed property access (get_settings().property).

    8. Container-Native Environment Injection (Zero-Touch Cloud Migration):

    9. Cloud secret engines inject secrets directly into container environment variables at deployment time:
      • Google Cloud Platform (Cloud Run / GKE): Secret Manager secrets map to container environment variables via deployment configuration (specifically: gcloud run deploy --set-secrets="TAVILY_API_KEY=tavily-key:latest").
      • Amazon Web Services (ECS / EKS): AWS Secrets Manager and SSM Parameter Store inject secrets into container task definitions (secrets: [{name: "TAVILY_API_KEY", valueFrom: "..."}]).
      • Microsoft Azure (Container Apps / AKS): Azure Key Vault secrets map into container environment variables.
      • Kubernetes / On-Premise: HashiCorp Vault Agent or Kubernetes Secret Store CSI Driver injects secrets into container pods as standard environment variables.

    10. BaseSettings hydrates these transparently upon application startup. Switching cloud providers modifies infrastructure configuration exclusively, leaving MCP tools, dispatcher logic, and Python services 100% untouched.

    11. Future-Proof Dynamic Secret Rotation Architecture:

    12. If enterprise requirements evolve to demand runtime dynamic secret polling or ephemeral token renewal (specifically: rotating short-lived Vault tokens without container restarts), Pydantic's native PydanticBaseSettingsSource in @[backend_v2/settings.py] provides the single pluggable extension point. Tool implementations (TavilyTool, WikipediaClient) remain completely unaware of the underlying secret retrieval engine.

    """Registry and dispatcher for MCP tools."""

    def __init__(self, tools: list[BaseTool]) -> None:
        self._registry: dict[str, BaseTool] = {tool.tool_id: tool for tool in tools}
        self._capability_index: dict[ToolCapability, list[BaseTool]] = {
            cap: [] for cap in ToolCapability
        }
        for tool in tools:
            self._capability_index[tool.capability].append(tool)

    def get_declarations(self, allowed_tools: list[str]) -> list[MCPToolDeclarationDTO]:
        declarations: list[MCPToolDeclarationDTO] = []
        for tool_id in allowed_tools:
            if tool_id in self._registry:
                declarations.append(self._registry[tool_id].declaration)
        return declarations

    def get_tools_by_capability(
        self, allowed_tools: list[str], capability: ToolCapability
    ) -> list[BaseTool]:
        """Return allowed tools implementing the specified capability preserving allowed_tools order."""
        allowed_set = set(allowed_tools)
        if capability not in self._capability_index:
            return []
        return [
            self._registry[t_id]
            for t_id in allowed_tools
            if t_id in self._registry and self._registry[t_id].capability == capability
        ]

    def resolve_primary_search_tool(self, allowed_tools: list[str]) -> BaseSearchTool | None:
        """Resolve primary search tool preserving explicit step configuration priority.

        The order of tools in allowed_tools defines the precedence hierarchy.
        Returns the first tool matching ToolCapability.SEARCH, or None if no search tool is allowed.
        """
        for tool_id in allowed_tools:
            if tool_id not in self._registry:
                continue
            tool = self._registry[tool_id]
            if tool.capability == ToolCapability.SEARCH and isinstance(tool, BaseSearchTool):
                return tool
        return None

    def has_capability(self, allowed_tools: list[str], capability: ToolCapability) -> bool:
        """Check if any allowed tool implements the given capability."""
        return len(self.get_tools_by_capability(allowed_tools, capability)) > 0
