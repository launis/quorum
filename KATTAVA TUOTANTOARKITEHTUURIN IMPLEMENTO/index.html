    Tietokantaa ei koskaan kysellä jokaisella saapuvalla HTTP-pyynnöllä: 1.     3.2 Redis Fail-Closed Kill-Switch

    Jos ylläpitäjä sulkee käyttäjätilin, muuttaa roolia tai käyttäjä poistetaan GDPR-pyynnöllä: * Backend kirjoittaa välittömästi Redisiin avaimen revoked:usr:{user.id} (TTL = 900 s). * Jokainen API-kutsu tarkistaa O(1) nopeudella Redisistä, ettei käyttäjä ole estolistalla. * Fail-Closed: Jos Redis-yhteys katkeaa, järjestelmä palauttaa 503 Service Unavailable, estäen oikeuksien vuotamisen.

    Organisaatiot voivat tuoda omat LLM- ja MCP-avaimensa: * Avaimet salataan Cloud KMS Envelope Encryption -menetelmällä tai tallennetaan GCP Secret Manager -viitteinä. * Avaimet puretaan EPIC 160:ssä luotavassa [NEW] SecretService-palvelussa pyyntökohtaisesti pydantic.SecretStr-muotoon ja injektoidaan LLM- ja MCP-kutsuille ilman lokivuotoja.

    Luku 4: Firebase Storage ja Direct-to-Cloud Signed URLs

    Raskaat binäärit (PDF-raportit, syötetiedostot) eivät saa koskaan kulkea Python-backendin RAM-muistin läpi.

    4.1 Latausputki (Upload Flow)

    1. Pyyntö: Frontend pyytää API:lta latauslupaa: POST /api/v2/files/upload-request (tiedoston nimi, koko, MIME-tyyppi).
    2. Rekisteröinti: Backend luo tietokantaan file_metadata-rivin tilaan pending.
    3. Signed URL: Backend luo Firebase Admin SDK:lla aikarajatun (15 min) PUT-osoitteen, johon sidotaan sallittu tiedostokoko ja MIME-tyyppi.
    4. Suoralataus: Frontend lähettää binäärin suoraan Firebase Storageen.
    5. Vahvistus: Frontend kutsuu POST /api/v2/files/{id}/confirm, jolloin backend varmistaa tiedoston olemassaolon pilvessä ja asettaa tilaksi uploaded.
