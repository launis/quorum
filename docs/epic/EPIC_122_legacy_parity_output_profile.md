# EPIC 122: Legacy Parity Output Profile (Strict SDUI)

> [!NOTE]
> **Scientific & Industrial Validation (2025-2026)**
> Recent industry standards (2026) for Server-Driven UI (SDUI) dictate that database schemas should prioritize modularity, strict contract enforcement, and versioning. All visual components must flow through a unified SDUI pipeline with strict Pydantic-enforced contracts.

## 1. Goal Description & Background (Objective & Problem Statement)

> [!CAUTION]
> **EPIC 121 STRATEGIC DEPENDENCY**
> EPIC 122 MUST be implemented completely BEFORE EPIC 121. The complex Output Profile payloads generated by this Epic (`content_blocks`, multi-layout sequences) are required as test data to stress-test the Admin Studio editor built in EPIC 121.

**Objective**: The user requires a PDF output that perfectly matches a historical legacy report format (e.g., pre-EPIC 110/120) but implemented strictly using the modern "Dumb Painter" SDUI architecture. 

> [!IMPORTANT]
> **ZERO EXCEPTION MANDATE (UNIVERSAL COMPLIANCE)**
> ALL reports and printouts (both PDF and Flutter UI) MUST be generated exclusively using this newly defined SDUI architecture pipeline. There are NO exceptions. Legacy bypasses, hardcoded UI logic that ignores the payload, or "backdoor" renderings are strictly forbidden. Every single report must flow through this unified data contract.

**Specific Requirements**:
1. **Header with Expanded Metadata**: The top header (green box) must display the core titles and an expanded set of general metadata (Timestamp, ID, Organization, plus new fields like User, Scoring Engine, and Strictness). Titles are resolved from the `I18nText` locale resolution chain (English master → target locale).
2. **Fixed Content Sections Inside the Summary Card**: Static text preambles must be injected directly *inside* the summary layout card via `I18nText`-wrapped `content_blocks`, immediately preceding the AI-generated synthesis text. The preamble text is defined in the master `en` locale and translated to target locales (e.g., `fi`).
3. **User Role in Synthesis**: The user's role must be integrated as part of the synthesis block flow. The LLM synthesizes the role dynamically in the **target output language** based on the `OutputProfile.language` field — no hardcoded locale strings in prompts.
4. **2D Scatter Chart Layout**: A dedicated layout block for detailed scoring must render a synthesis box and a 2D scatter chart between the global summary and the matrix.
5. **Dynamic XAI Extensions**: Output extensions (e.g., justification, coaching, counter-arguments) must be mapped dynamically from the backend using `extension_labels` with `I18nText` — no hardcoded locale-specific titles in Jinja or Flutter.
6. **Unified Matrix Tables**: All matrix printouts must display row explanations, scores, and atom hit distributions in a single unified table. Column headers are resolved via `matrix_column_labels` `I18nText` objects.
7. **View-Only Matrix with External Edit Link**: The matrix will be rendered as a strictly view-only component in both Flutter and PDF to guarantee 100% visual parity (matching the exact table structure in the provided reference image). Atom overrides will NOT be handled via interactive UI elements inside the matrix rows; instead, editing capabilities will be provided via a separate external link.

**Problem Statement**: The legacy PDF relied on hardcoded Jinja logic to achieve this layout. Under the new architecture, `report_template.jinja2` is a dumb consumer. Therefore, all these requirements must be satisfied by carefully configuring the `OutputProfile` JSON structure inside the Single Source of Truth (`seed_data.json`).

## 2. Architectural Impact & Compliance Matrix

### Deprecations & Sunset List (`What We Will REMOVE`)
- **None**: This Epic is purely additive to the seed data configuration. No domain code or existing templates will be deprecated.

### Retained SSOT Invariants (`What We Will RETAIN`)
- **`seed_data.json` Sovereignty**: The `OutputProfile` definition within the seed data remains the absolute authority over what is printed.
- **Dumb Painter Law**: `report_template.jinja2` will not be modified to hardcode any of these new fields; it will dynamically render whatever `ReportDataDTO` provides.

### Compliance & Modernity Gates
1. **Pydantic Strictness**: The JSON modifications must perfectly map to the `OutputProfile` Pydantic model (`ConfigDict(strict=True, extra='forbid')`).
2. **Zero Legacy State Support Mandate**: The changes will be applied to the master seed file, followed by a clean DB re-seed (`uv run python backend_v2/seed/run_seed.py local`).

### Producer-Consumer Integration Check
- **Producer (Backend Seed)**: Configures `visible_metadata`, `content_blocks`, and `layouts[0].matrix_visible_columns` inside `seed_data.json`.
- **Consumer (Jinja PDF)**: Iterates over the arrays provided by the producer to render the expanded header, static blocks, and combined matrices.

## 3. Phased Execution Plan (Implementation Strategy)

### Phase 1: OutputProfile Configuration in `seed_data.json`
We will surgically modify the target `OutputProfile` (e.g., `holistic_audit`) in @[c:\src\quorum\backend_v2\seed\seed_data.json] to include:

1. **Expanded Header Metadata**:
   Update the `visible_metadata` array to include more general data points.
   **CRITICAL**: Field keys MUST match the existing codebase defaults (`user`, `scoring_engine`, `strictness`) — NOT invented suffixed variants.
   ```json
   "visible_metadata": [
     "date",
     "execution_id",
     "organization",
     "user",
     "scoring_engine",

   ]
   ```

2. **Fixed Content Sections (`content_blocks` injected into Synthesis Card)**:
   Add a `MarkdownBlock` to the `content_blocks` array. In the V2 architecture (via `blueprint.py`), `content_blocks` are automatically prepended to the `synthesis_blocks` array of the first layout that has `is_synthesis_enabled=True`. This guarantees they render perfectly *inside* the summary card, right above the dynamic LLM text.

   > [!IMPORTANT]
   > **I18n Mandate**: The `text` field in `MarkdownBlock` is a raw string, NOT an `I18nText`. Static preamble text that requires localization MUST instead use the `custom_preface` field on the `OutputProfile` (which is `I18nText`), or be moved to Flutter `.arb` files. Hardcoding Finnish in `content_blocks.text` is acceptable ONLY for tenant-specific profiles where the organization language is fixed. For international profiles, use `custom_preface` with full `I18nText`.

   ```json
    "custom_preface": {
      "default_locale": "en",
      "translations": {
        "en": "**Report on your AI skills**\n\nThis report analyzes your approach to utilizing AI...",
        "fi": "**Raportti tekoälytaidoistasi**\n\nTämä raportti analysoi tapaasi hyödyntää tekoälyä..."
      }
    }
   ```

## 6. Identified Missing Parity Requirements (Red-Teaming)

During historical analysis of the legacy PDF and old Jinja templates, several critical missing elements were identified that MUST be handled by this Epic to achieve true parity:

1. **Missing Matrix Columns**: The old template explicitly rendered `normalized_score` (the green percentage pill) alongside `distribution`. This has been added to `matrix_visible_columns` in the plan.
2. **Missing XAI Extensions**: The PDF contains dynamic synthesis blocks for "ARJEN VINKKI", "VASTA-ARGUMENTTI", and "KORJAAVAT TOIMENPITEET". These have been added to `visible_block_extensions` and `extension_labels` in the plan.
3. **Execution ID in Metadata**: The PDF header displays `ID: exe_...`. The `visible_metadata` array must be updated to include `execution_id` alongside `date` and `organization`.
4. **Global Score (Kokonaiskeskiarvo)**: The PDF renders a large "Kokonaiskeskiarvo 19.30/100" at the bottom of the Summary card. The backend SDUI mapping (via `blueprint.py`) must ensure this is passed to the frontend (likely via a `score_display_label` or a specific SDUI block), strictly adhering to the Dumb Painter KI.
5. **Penalties & System Audit Trail (New SDUI Definition)**: While the visual design of the legacy Jinja templates (red box for penalties, audit trail layout) will be maintained, their **definition and data delivery must be done completely in the new SDUI way**. They must be explicitly mapped as standard SDUI layout blocks inside the `OutputProfile`, rather than relying on legacy fallback arrays like `penalties_applied` or `mcp_tool_audit`. **Crucially, strict Flutter/UI and PDF parity MUST be maintained.** The Flutter client will render these mapped SDUI blocks identically to the PDF.
6. **Jargon/Slop Ratio Scale (Jargon-sanojen suhteellisuus)**: The report must show the ratio of AI jargon words versus other words. Its visual design matches the old template, but its **definition is handled purely in the new SDUI format** (e.g., converted into a specific matrix item or layout block by the backend). The Flutter UI must replicate this visual scale exactly based on the SDUI payload.
7. **Printable Sources (Tulostettavat lähteet)**: The report must explicitly print the source URLs/references used. Its visual design matches the old template, but its **definition is handled purely in the new SDUI format** (e.g., as a dedicated source list SDUI block). The Flutter UI must also render these sources at the end of the document via the new SDUI pipeline with identical styling.
8. **Universal Enforcement (Ei poikkeuksia)**: ALL outputs and reports, without exception, must be rendered using this exact new methodology. No legacy fallbacks or alternative rendering paths are permitted to bypass this strict SDUI pipeline.
