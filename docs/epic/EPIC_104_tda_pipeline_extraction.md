# EPIC 104: TDA Pipeline Extraction & Strategy Injection

## 1. Goal Description
The Quorum Phase 3 architecture orchestrates LLM executions through `LLMNodeStrategy` (in `llm.py`). Currently, `llm.py` acts as a monolithic "God Class" by serving as both the SSOT Lifecycle Manager (handling pre-hooks, schemas, post-hooks, telemetry, and anomaly retries) AND the execution engine. Specifically, lines 560-612 of `llm.py` contain a hardcoded, inline execution of the Topological Data Analysis (TDA) pipeline (`TwoPassAtomizer` → `SlidingWindowLinker` → `EnrichedDagExecutor` → `ResultProjector`).

**Objective**: Decouple the execution logic from the lifecycle management. Extract the inline TDA pipeline into a standalone, injectable `ExecutionEngine` following the Composition/Strategy Injection pattern. This resolves major Single Responsibility Principle (SRP) and Open-Closed Principle (OCP) violations, enabling the future integration of diverse execution paths (e.g., standard RAG, MCP tool loops, direct LLM generation) without modifying the core `LLMNodeStrategy`.

## 2. Architectural Impact & Safeguards
- **Structural Subtyping via Protocol & Strict DTOs**: We will introduce an `ExecutionEngine` Protocol instead of an ABC. This adheres to Quorum's lightweight duck-typing rules for strategy injection. The Protocol will enforce a single `execute()` method that MUST return a strictly defined Pydantic DTO (e.g., `EngineExecutionResult`), NEVER a raw dictionary (`dict[str, Any]`). This ensures full Pydantic V2 validation, determinism, and IDE support.
- **Strict Lazy-Load Typing (`TYPE_CHECKING`)**: The use of `Any` to bypass lazy loading typing is strictly forbidden. The only approved method to resolve type hinting for lazy imports is using Python's `from typing import TYPE_CHECKING`.
- **Zero Cold Start Protection (Lazy Loading)**: The existing `llm.py` uses inline imports to avoid loading the heavy AI pipeline components globally. However, moving the pipeline to a dedicated `tda_engine.py` means the sub-services (which are standard Quorum modules) can be imported at the top-level of `tda_engine.py`. To protect the global execution pipeline from PyO3 initialization delays and cold start bloat (per the `inline_imports_ban` exception), concrete engines like `TDAEngine` will be **lazily imported** purely inside the Composition Root (`dag_executor.py` wiring logic). `LLMNodeStrategy` MUST NOT import or instantiate any concrete engine, preserving true Inversion of Control (IoC).
- **Fail-Fast & Explicit DI (No Fallbacks)**: The new `engine` parameter in `LLMNodeStrategy` MUST be mandatory. There will be no `Any | None = None` defaults and no dynamic `TDAEngine` instantiation inside the strategy. This strictly enforces Dependency Injection and Fail-Fast principles. All existing unit tests and workflow logic must be updated to explicitly inject the required engine.
- **Strict Anomaly Propagation & Anti-Corruption Layer (ACL)**: The `ExecutionEngine` Protocol MUST explicitly require engines to raise standard Quorum exceptions (e.g., `AppException`, DLQ errors) for transient failures or anomalies. Engines MUST NOT swallow errors silently. Furthermore, the engine MUST act as an **Exception Anti-Corruption Layer (ACL)**: any raw, third-party exceptions (e.g., Pydantic's `ValidationError`, native `KeyError`) originating from within the engine's sub-services MUST be caught and wrapped into a Quorum-compliant exception (e.g., `EngineExecutionException`). This ensures `llm.py`'s retry loops and DLQ routing can deterministically handle them without crashing the DAG unexpectedly. The wrapper MUST enforce the Dual-Reporting (RFC 7807) pattern by executing a structured `logger.error` detailing the logical reason before raising the exception.
- **Absolute Engine Statelessness**: The `ExecutionEngine` MUST be strictly stateless across `execute()` calls. It MUST NOT store runtime execution state (e.g., intermediate results, buffers) in `self` variables. This is critical to prevent race conditions and memory leaks during highly concurrent, multi-threaded DAG executions.
- **Strict DTO Definition & Location**: To prevent black-box ambiguity and circular dependencies, `EngineExecutionResult` MUST be defined in a dedicated central location (e.g., `backend_v2/models/dtos/engine.py`). It MUST explicitly declare its schema (e.g., `results: list[AtomResultProjection]`, `hydrated_references: dict[str, HydratedAtomDTO]`) so the contract between the engine and the orchestrator is absolutely clear without relying on heavy imports.
- **Observability Black Hole Prevention (Live Telemetry Flush)**: The engine MUST NOT buffer telemetry (e.g., `TraceEvent` objects) exclusively in local memory to be returned at the end. If the engine crashes mid-execution, buffered telemetry is lost, creating an observability black hole. The engine MUST flush telemetry on-the-fly via a `trace_callback` or injected `audit_repo` so that partial execution traces survive catastrophic engine failures.
- **Dependency Starvation Prevention**: Engine constructors MUST receive all required collaborators explicitly via constructor injection. For `TDAEngine`, this is limited to the `PromptCompiler` (which the existing sub-services already require). Future engines (e.g., `SynthesisEngine` in Epic 105) MAY require additional dependencies. Do NOT inject full Repository interfaces or `arq_pool` into `TDAEngine` — the TDA pipeline does not natively require them.
- **Concurrency & Cancellation Integrity**: The `execute()` method MUST explicitly accept and respect the orchestrator's `semaphore: asyncio.Semaphore` and `running_event: asyncio.Event | None`. Dropping these tokens would cause the engine to blindly violate rate limits (429) and become immune to DAG cancellation mid-flight.
- **Parameter Object Pattern (Anti-Creep)**: The `execute()` signature MUST NOT suffer from a "Long Parameter List" (Parameter Creep). All runtime variables MUST be encapsulated within a single `EngineExecutionRequest` DTO. This prevents the `ExecutionEngine` Protocol from becoming brittle when future orchestration features are added.
- **Append-Only Law & Seed Data Validation**: Executions (results) MUST NOT and do not need to be migrated during refactoring. **Historical execution data has zero structural value and is considered entirely disposable during migrations.** Historical payload data is append-only and mutation is strictly prohibited. ONLY `seed_data.json` is updated for configuration changes. Any modifications to `seed_data.json` MUST strictly follow the *Vault Mutation Protocol* (e.g., re-seeding via `run_seed.py`).

## 3. Implementation Phases

### Phase 0: Protocol Prerequisites & Directory Structure
- **Target Folder**: Create the `backend_v2/services/orchestrator/engines/` directory with an `__init__.py` file. This folder will house all extracted execution engines.
- **DTO Definition (`models/dtos/engine.py`)**: Define the `EngineExecutionRequest` and `EngineExecutionResult` structures here to prevent circular imports before building the protocol.
  - `EngineExecutionResult` MUST be a pure Pydantic V2 model enforcing `model_config = ConfigDict(strict=True, extra='forbid', frozen=True)` to prevent mutation of execution states.
  - `EngineExecutionRequest` holds complex runtime objects (`LLMClient`, `Semaphore`, `Callable`). It MUST be defined as a Python `@dataclass(frozen=True)` (or Pydantic with `arbitrary_types_allowed=True`) to bypass JSON serialization constraints while maintaining immutability.

### Phase 1: ExecutionEngine Protocol & TDA Engine Extraction
- **Protocol Definition (`engines/base.py`)**: Define the `ExecutionEngine` Protocol. To prevent "Parameter Creep" and ensure future-proofing, the `execute()` signature MUST accept exactly one parameter: an `EngineExecutionRequest` Pydantic DTO (or dataclass), and return an `EngineExecutionResult` Pydantic DTO. 
- **EngineExecutionRequest Schema**: This request object MUST encapsulate all cognitive data (`compiled_schema`, `system_prompt` / `prompt_context`), orchestration constraints (`step: StepRule`, `context: StrategyContext`), standard payload (`bound_client`, `global_source_text`, `target_locale`), concurrency tokens (`semaphore: asyncio.Semaphore`, `running_event: asyncio.Event | None`), and live observability hooks (`progress_callback`, `trace_callback: Callable[[TraceEvent], Awaitable[None]]`). The engine MUST explicitly propagate the `semaphore` and `running_event` down to its sub-services for use in `asyncio.TaskGroup` constraints.
- **Context Contract Clarification**: The `GlobalAtomBlackboard` is written by `dag_executor.py`'s `_execute_preflight_pipeline()` at the DAG orchestration level — NOT by `TDAEngine` or `LLMNodeStrategy`. `StrategyContext` is `frozen=True`, making direct writes to `context.context_variables` physically impossible from within an engine. `TDAEngine` has zero involvement with the blackboard lifecycle. Downstream engines (Epic 105's `SynthesisEngine`) will read the blackboard from `request.context.context_variables` as a consumer only.
- **TDA Engine Implementation (`engines/tda_engine.py`)**: Move the entire inline block from `llm.py` into this engine. 
- **Top-Level Standard Imports**: Import the 5 sub-services (`LLMTaskExecutor`, `TwoPassAtomizer`, `SlidingWindowLinker`, `EnrichedDagExecutor`, `ResultProjector`) globally at the top of `tda_engine.py`. These are standard modules (not native ML extensions), meaning they belong at the top level to adhere to Quorum's strict `inline_imports_ban`.
- **Configuration Segregation (`strict_configuration_segregation` Compliance)**: The current inline code hardcodes `SlidingWindowLinker(window_size=4, overlap=2)`. When moving to `TDAEngine`, these values MUST be sourced from `backend_v2/settings.py` (e.g., `get_settings().tda_linker_window_size`, `get_settings().tda_linker_overlap`). You MUST add these fields to `GlobalSettings` in `settings.py` if they do not exist. Hardcoding configuration values inside the engine violates the Global Config Sovereignty rule.

### Phase 2: LLMNodeStrategy Refactoring
- **Constructor Override (`strategies/llm.py`)**: Override `LLMNodeStrategy.__init__` to accept all `NodeStrategy` positional arguments plus a mandatory `engine` parameter implementing the `ExecutionEngine` Protocol. Use `from typing import TYPE_CHECKING` at the top of the file to type hint the engine parameter without triggering a runtime import.
- **Explicit Delegation**: Replace the 50-line inline TDA pipeline with a single `await self._engine.execute(...)` delegation. The strategy will not instantiate the engine itself. `llm.py` strictly retains ownership of telemetry, schema compilation, trace event generation, **AND the anomaly retry loop**. The `while retry_count <= MAX_RETRIES` loop driven by post-hook anomaly detection is a lifecycle concern and MUST NOT be extracted into the engine.

### Phase 3: DAG Executor Wiring
- **Explicit DI Injection (`dag_executor.py`)**: Update the `NodeExecutor.execute()` step routing logic. When instantiating `LLMNodeStrategy` (e.g., strictly in the `"reasoning"` branch), explicitly inject the engine with its precise dependencies: `TDAEngine(compiler=self.compiler)`. Do NOT inject full Repositories or `arq_pool` as the TDA pipeline does not natively require them, preventing "God Object" dependency inflation. **NO DEFAULT FALLBACKS**: The default `else` branch MUST NOT route to `TDAEngine`. It MUST immediately raise a Fail-Fast exception (e.g., `UnknownStrategyError`) if the step's `model_strategy` is unrecognized AND `step.engine_override` is not a recognized `EngineOverrideStrategy` value, ensuring strict compliance with the "No Fallbacks" rule.
- **`engine_override` Awareness (CRITICAL)**: The existing routing at `dag_executor.py` uses a compound condition: `step_def.model_strategy == "synthesis" or step.engine_override == "PRE_HYDRATED_SYNTHESIS"`. You MUST preserve the `engine_override`-based routing for `PRE_HYDRATED_SYNTHESIS` (Epic 105 will later refactor this branch). You MUST also preserve awareness of `DYNAMIC_TOOL_AGENT` in the routing enumeration. The Fail-Fast `else` branch triggers only when BOTH `model_strategy` and `engine_override` yield no recognized routing.
- **Lazy DI Import**: Perform the `from backend_v2.services.orchestrator.engines.tda_engine import TDAEngine` inline within the conditional branches, exactly matching the existing resilient pattern used for `PreHydratedSynthesisStrategy`.

## 5. Synthesis & Architectural Alignment
TDA-suoritusputken eristäminen on loistava veto SRP- ja OCP-periaatteiden kannalta. Se on kuitenkin toteutettava ehdottoman tyyppiturvallisesti. Poistamalla "laiskat" fallbackit ja pakottamalla Pydantic-mallien käyttö `ExecutionEngine`-rajapinnassa saavutamme arkkitehtuurin, johon on helppo lisätä myöhemmin uusia malleja (kuten MCP-työkalujen kutsumoottoreita) turvallisesti.
