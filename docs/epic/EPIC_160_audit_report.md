## 1. Executive Summary & Root Cause Analysis of Hardened Findings

During the Tier 0 System 2 adversarial cross-examination and deterministic pre-flight audits (`scripts/audit_markdown_boundaries.py`, `scripts/audit_technical_debt.py`, `scripts/audit_flutter_theme_sovereignty.py`, and `scripts/audit_epic_coverage.py`), `@[docs/epic/EPIC_160_B2B_SaaS_IAM_and_Enterprise_Hardening.md]` was evaluated against Quorum 2026 architectural invariants. Twelve red-team hardening items (`RT-160-01` through `RT-160-12`) were verified and locked into the Epic:

1. **RT-160-01: Complete Touched-Scope Technical Debt & Theme Sovereignty Census in Phase 1**
   - **Root Cause**: `audit_technical_debt.py --plan docs/epic/EPIC_160_B2B_SaaS_IAM_and_Enterprise_Hardening.md` and `audit_flutter_theme_sovereignty.py` require 100% of touched-scope warnings to be inventoried so `--strict` exits with `0` findings.
   - **Architectural Justification**: Under `touched_scope_tech_debt_mandate`, Phase 1 and Phase 2 resolve 100% of live touched-scope technical debt (`identity.py`, `test_auth.py`, `test_auth_validator.py`, `test_integration_real_llm.py`, and `scripts/run_e2e_variance_test.py`) while confirming `login_screen.dart` and `new_execution_view.dart` pass `audit_flutter_theme_sovereignty.py` with `0` violations.

2. **RT-160-02: RFC 7807 Dual-Reporting & `QGR009` Error Code Debt in `@[backend_v2/api/dependencies.py#L379-L403]` & `@[backend_v2/api/dependencies.py#L410-L454]`**
   - **Root Cause**: Physical inspection of `@[backend_v2/api/dependencies.py#L379-L403]` confirmed a raw string literal `error_code = "AUTH_TOKEN_MISSING"` instead of `ErrorCodes.AUTHENTICATION_FAILED.value`. Furthermore, `require_role` (`@[backend_v2/api/dependencies.py#L410-L454]`) raises `PermissionDeniedError` without a preceding `logger.error` call and without `"error_code": ErrorCodes.PERMISSION_DENIED.value` in `details`.
   - **Architectural Justification**: Modifying `dependencies.py` in Phase 2 triggers `backend_audit_loop.py --ast-strict` (`QGR009` and `rfc7807_dual_reporting_mandate`). Phase 2.2 and Section 2.5 Row 4 mandate replacing `"AUTH_TOKEN_MISSING"` with `ErrorCodes.AUTHENTICATION_FAILED.value` and adding structured RFC 7807 `logger.error` + `ErrorCodes.PERMISSION_DENIED.value` in `require_role`.

3. **RT-160-03: Deterministic Pre-Provisioned Account Binding Invariant in `TokenService.exchange_firebase_token`**
   - **Root Cause**: Pre-provisioned account lookup requires strict email verification and UID collision guards when Phase 1.2 directs to create `TokenExchangeRequestDTO` and create `TokenExchangeResponseDTO` in `@[backend_v2/models/auth.py]`.
   - **Architectural Justification**: To comply with `zero_backward_compatibility_planning_ban` and `single_pipeline_invariant_mandate` and prevent account takeover via unverified IdP emails, Phase 2.1 requires `email_verified is True` on the Firebase token and `user.firebase_uid is None` on the pre-provisioned `User` record, raising `ConflictError` (`ErrorCodes.USER_ALREADY_ASSIGNED`) if `user.firebase_uid` is already bound to a different UID.

4. **RT-160-04: Asynchronous BYOK Pre-Resolution & Zero-Fallback Enforcement in `GenericMCPClient`**
   - **Root Cause**: Physical inspection of `@[backend_v2/services/mcp/generic_mcp_client.py#L237-L292]` confirmed that `_build_request_headers(self, gateway: SystemConfigMCPGateways) -> dict[str, str]` is synchronous, whereas when Phase 1.2 and Phase 3.1 create `SecretService` in `[NEW] @[backend_v2/services/auth/secret_service.py]` and create `ResolvedCredentialDTO` in `@[backend_v2/models/auth.py]`, `resolve_mcp_credential` performs asynchronous I/O against PostgreSQL and Cloud KMS / Secret Manager.
   - **Architectural Justification**: Phase 3.2 and Section 2.5 Row 3 specify that `GenericMCPClient` and `ToolDispatcher` resolve `ResolvedCredentialDTO` asynchronously via `await secret_service.resolve_mcp_credential(...)` before invoking synchronous `_build_request_headers`, and `SecretService` raises `ConfigurationError` (`ErrorCodes.SECRET_RESOLUTION_FAILED`) immediately if a configured tenant secret fails KMS decryption or Cloud Secret Manager lookup.

5. **RT-160-05: Monolith Decomposition Path Synchronization & AST Boundary Alignment (`MBD003` & `MBD004`)**
   - **Root Cause**: `backend_v2/llm/provider.py` was decomposed into `backend_v2/llm/provider/` (`litellm_provider.py` and `provider_factory.py`), `backend_v2/database/postgres/entity_adapter.py` was decomposed into `backend_v2/database/postgres/entity_adapter/` (`__init__.py`, `coercion_and_constants.py`, `iam_and_system_stage.py`, `seed_and_collection_stage.py`), and `backend_v2/services/orchestrator/strategies/llm.py` was decomposed into `backend_v2/services/orchestrator/strategies/llm_strategy/__init__.py` (`QGR017`).

   - **Root Cause**: Enterprise B2B SaaS compliance in 2026 requires mandatory 2FA (`firebase.sign_in_second_factor`), single-session vs. global logout (`POST /api/v2/iam/auth/logout` where Phase 1.2 directs to create `LogoutRequestDTO` and create `LogoutResponseDTO`, paired with `MGET revoked:usr:{id} revoked:jti:{jti}`), headless CLI token exchange with 13-minute auto-refresh (where Phase 1.2 directs to create `CliSessionStateDTO`), 4-Tier RBAC (`VIEWER`/`MEMBER` vs. `MANAGER` vs. `ADMIN` vs. `ROOT`), and SafeLinks-immune time-bound task assignments (`ExecutionAssignment` / `tsk_<hex32>` where Phase 5.4 directs to create `ExecutionAssignmentService`).
   - **Architectural Justification**: Locked two-layer 2FA enforcement, Dual-Key `MGET` revocation, `ExecutionAssignmentService`, and the three separated Flutter views (`UserProfileSettingsView`, `OrganizationIamSettingsView`, and `TaskAssignmentPortalView`) across Phases 1 through 6.

11. **RT-160-11: Enterprise Best-Practice Hardening (RFC 8693 `act` Impersonation Claim, Auth Edge Rate Limiting, NIST SP 800-57 `kek_version`, `allowed_email_domains` Domain Lock & Pre-Exchange Revocation Guard)**
    - **Root Cause**: Five surgical enterprise B2B SaaS safeguards were identified across files already touched by EPIC 160: (1) `create_impersonation_token` (`@[backend_v2/services/auth/token_service.py#L32-L232]`) and `impersonate_user` (`@[backend_v2/api/routers/iam/auth.py#L107-L148]`) lacked full stateless RAM claims (`org`, `role`, `mfa`, `jti`), RFC 8693 Section 4.1 `act` (`actor_id`), and mandatory `reason` auditing; (2) public unauthenticated auth/invitation/assignment endpoints needed edge IP brute-force protection in `TenantRateLimitService`; (3) `tenant_secrets` envelope encryption needed `kek_version` for zero-downtime NIST SP 800-57 KMS master key rotation; (4) `Organization` needed optional `allowed_email_domains` domain locking for invitations and task assignments; and (5) `TokenService.exchange_firebase_token` needed a pre-exchange `RevocationCache` check so revoked users cannot mint a new JWT during the 13-minute background refresh.
    - **Architectural Justification**: Locked all five safeguards into Phases 1.1, 1.2, 1.3, 2.1, 2.2, 3.1, 4.2, 5.1, 5.4, and Section 4.1 DoD.

12. **RT-160-12: Cohort Batch Task Assignments & Invitations (`POST .../assignments/batch` & `POST .../invitations/batch`) via Multi-Email Copy-Paste, RFC 4180 CSV Import & Atomic `conn.executemany`**
    - **Root Cause**: Enterprise B2B organizations frequently onboard or assign timed tasks to cohorts of 10–500 participants at once; single-recipient creation requires repetitive manual clicks, while sharing a single token across multiple participants would violate per-user identity binding, independent countdown timers (`activated_at`), and single-shot submission isolation (`execution_id`).
    - **Architectural Justification**: Extended Phase 1.2, Phase 1.3, Phase 5.1, Phase 5.4, and Phase 6.2 to add `batch_id` to `ExecutionAssignment` (`execution_assignments`), Create `InvitationBatchCreateDTO`, Create `InvitationBatchResponseDTO`, Create `ExecutionAssignmentRecipientDTO`, Create `ExecutionAssignmentBatchCreateDTO`, and Create `ExecutionAssignmentBatchResponseDTO` in `@[backend_v2/models/auth.py]` and `@[backend_v2/models/domain/execution.py]`, implement `OrganizationService.create_invitation_batch` (`POST /api/v2/iam/organizations/{org_id}/invitations/batch`) and `ExecutionAssignmentService.create_assignment_batch` (`POST /api/v2/execution/executions/assignments/batch`) with all-or-nothing pre-flight validation (`allowed_email_domains`, 1:1 Identity Collision Guard, and email deduplication) and atomic PostgreSQL 19 `conn.executemany` insertion of unique per-recipient `tsk_<hex32>` and 256-bit tokens, and support Multi-Email Copy-Paste (`InputChip` parsing) and RFC 4180 `.csv` upload (`email,name,language`) with `.csv` Magic Link export in `NewExecutionView` and `OrganizationIamSettingsView`.

13. **RT-160-13: Autonomous Transactional Email Delivery (`EmailService` via `httpx.AsyncClient` Batch HTTPS API on Port `443`, `console` Dev Mode, `qrum.ai` Link Construction & Token-Rotating Resend)**
    - **Root Cause**: GCP Cloud Run (`quorum-api` and `quorum-worker` in `europe-north1` per `@[docs/implementationplans/IMPLEMENTATION_PLAN_GCP_Production_Deployment.md]`) blocks outbound SMTP port `25`, while B2B Organization Invitations (`Invitation`) and Time-Bound Cohort Task Assignments (`ExecutionAssignment`, 1–500 recipients) require autonomous personalized email delivery containing task metadata (`organization_name`, `workflow_name`, `hard_deadline_at`, `relative_duration_seconds`, and per-recipient `https://app.qrum.ai/task/<raw_token>` URLs) without adding new third-party SDK dependencies (`dependency_hallucination_firewall`).
    - **Architectural Justification**: Extended Phase 1.1 (`@[backend_v2/settings.py]`), Phase 1.2 (`@[backend_v2/models/enums.py]`, `@[backend_v2/models/auth.py]`, `@[backend_v2/models/domain/execution.py]`), Phase 1.3, Phase 5.1, Phase 5.4, and Phase 6.2 to Define `EmailTransportMode` (`CONSOLE = "console"`, `HTTP_API = "http_api"`) and Define `EmailDeliveryStatus` (`PENDING = "pending"`, `SENT = "sent"`, `FAILED = "failed"`), Create `TransactionalEmailItemDTO` (wrapping `action_url` in `SecretStr` to prevent cleartext token logging), Create `TransactionalEmailBatchResultDTO`, and Create `EmailService` in `[NEW] @[backend_v2/services/auth/email_service.py]` (with unit tests in `[NEW] @[backend_v2/tests/unit/services/auth/test_email_service.py]`) dispatching 1–500 personalized emails in a single bounded `httpx.AsyncClient` HTTPS `POST` request on port `443` from `no-reply@qrum.ai` in production (or structured `console` mode in local development, while Firebase Auth natively handles password reset and email verification emails), plus `POST /api/v2/execution/executions/assignments/{assignment_id}/resend` for token-rotating email resend alongside manual Copy Link / `.csv` export fallback.
